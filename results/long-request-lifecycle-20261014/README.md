# 64K 请求生命周期与恢复探针（2026-10-14）

## 观察

在旧版 64K 非流式 MindIEQ/原始 W4 交替测试中，第一轮请求都返回完整 usage。客户端随后在长连接/metrics 响应读取阶段等待，期间日志短暂显示 `Running: 1 reqs` 和非零 KV usage；容器随后回到 `Running: 0`。因此这次现象不能证明 Engine 或 KV 泄漏，主要暴露了 benchmark 端 HTTP 读取不可靠。

相关日志证据保留在 a2 实验机的容器日志中，时间窗口为 UTC `23:31`～`23:32`：原始 W4 在请求返回后仍显示 `Running: 1 reqs`；MindIEQ 同窗口回到 `Running: 0 reqs`。

## 恢复验证

为清理旧测试进程并建立干净基线，重启实验性原始 W4 容器 `qwen36-tp1-chip1-w4-c8-original-112k`。模型重新加载完成后，分别发送 512 token 输入、32 token 输出的非流式恢复探针：

| 端点 | 总耗时 | usage | 输出 |
|---|---:|---|---|
| MindIEQ `18024` | 1.63 s | 512 + 32 | 正常 |
| 原始 W4 `18028` | 1.96 s | 512 + 32 | 正常 |

两端 HTTP health 均为 200，恢复探针输出内容正常。该重启用于清理实验状态，不代表发现了确定的服务端泄漏。

随后在重启后的两个端点上各执行 3 次连续 512/32 非流式请求，耗时保持稳定：MindIEQ `1.56/1.56/1.56 s`，原始 W4 `1.80/1.80/1.80 s`。日志最终均回到 `Running: 0 reqs`，说明短请求路径在恢复后可连续工作；这仍不能覆盖 64K/112K 长请求的重复生命周期。

进一步的 32K 两轮交替测试也全部完成：MindIEQ Prefill 中位 `569.11 tok/s`、原始 W4 `453.21 tok/s`，两端 Decode 分别为 `29.12/28.79 tok/s`；四个请求完成后日志均回到 `Running: 0 reqs`。当前证据将风险范围缩小到 64K 及以上长请求，但尚未证明 64K 是精确触发阈值。

## 工程结论

- 当前 64K/112K 的单流速度和质量结果仍有效；修复后的工具已完成 64K 两轮交替，但这仍不是正式线上 P50/P95。
- 已修复 phase benchmark 的 metrics 连接处理：从 urllib 长连接读取改为带超时的 curl，并保留非流式 fallback。
- 仍需增加“长请求完成后短请求恢复、连续长请求、超时取消”测试；重启只用于清理旧实验状态，不是产品方案要求。

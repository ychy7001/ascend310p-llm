# WY FP64分阶段诊断（2026-11-07）

复用固定120快照、12触发和480边界输入，无设备窗口。CPU锁内分别58.25秒与41.80秒，两个进程ExitCode 0，容器已清除、锁可重取。现有FP32 oracle、阈值、协议、worker、R与生产kernel不变；本目录不是新的门禁裁决。

从捕获的FP16/FP32输入在构建累计gate和Gram之前转换为FP64，计算独立三角求解参考。另保留FP32构造的系数与RHS，再仅把求解提升为FP64，以区分系数构造与求解精度。最后单独比较输出转FP16的影响。仅分析W/U，不能替代完整模型验证。

## 1. FP32参考和最终FP16输出并非本批超差的充分原因

以下是相对FP64参考、沿用atol=0.0005/rtol=0.04统计的U超差元素数量，仅为诊断统计：

| 路径 | 120快照 | 12触发 | 480边界 |
| --- | --- | --- | --- |
| CPU FP32参考 | 0 | 0 | 0 |
| FP32系数、FP64求解 | 0 | 0 | 0 |
| FP64结果仅最终转FP16 | 0 | 0 | 0 |
| FP32系数，仅U RHS提前转FP16 | 103 | 20 | 224 |
| 设备Torch | 168 | 30 | 319 |
| 设备library-Gram旧候选 | 25 | 12 | 25 |

CPU FP32相对FP64的W/U平方误差很小；只做最终FP16 cast的W也无超差。因此不能把已观测到的设备超差全部归因于CPU FP32参考或最终FP16格式。提前舍入RHS能引入误差，但不表示它就是所有native分支的实际路径。

设备输出来自先前已拒绝的library-Gram候选（kernel SHA ecb8f121ae92738d2e8f992bd15acef09daba395115d6deae019e44ca46dbddd），不是原始native，也不是本轮新构建结果。

## 2. Gram输入中的beta乘入位置给出可验证的改进方向

复用该设备输出的累计gate，以CPU模拟两个64宽Gram分块和不同的beta乘入位置，统一用FP64三角求解并最终转FP16。该模拟不复现设备Cube累积、FP32逆矩阵、doubling或split apply的全部细节，不是设备输出的逐位模型。

| CPU模型的U超差元素 | 120快照 | 12触发 | 480边界 |
| --- | --- | --- | --- |
| beta*K先转FP16，再做Gram | 22 | 12 | 20 |
| 原始FP16 K做Gram，再FP32乘beta | 0 | 0 | 0 |

后者W同样无超差，误差接近只做最终FP16 cast的水平。前者与实际旧候选的触发集U平方误差约0.00542655相同、12个超差也相同，但这仍不证明其他输入所有偏差有唯一根因。

下一步隔离构建K/V=128 raw-K library Gram + FP32 beta postscale候选，保持scan、阈值、solve、W/U apply和输出格式不变，再以固定输入设备输出和原CPU FP32门禁裁决。累计g的严格no-worse问题单列，不能以W/U改善抵消。

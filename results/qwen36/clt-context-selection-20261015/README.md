# 48G / TP1 上下文与 C16/C8 选择表

结论：当前112K单流业务优先默认C16，C8保留为内存受限备选。相同容量核算C8约省1GiB，112K端到端Decode却下降17.8%–23.1%。该结论针对clt的310P1、相同W4A8/MTP1/Decode Graph、batch2048、max_num_seqs=1、prefix off、sync、util.90；不代表所有容量/并发/硬件档都默认C16。

## 现有服务的真实预留与速度

当前112K配置启动即预留缓存，业务输入变短不会释放预留池。不能将“一个8K请求”与“仅支持8K的服务”混为一谈。

|---|---:|---:|---:|---:|---:|
| 8192 | 40540 / 3675 | 35513 / 8702 | 589.54 / 30.11 | 586.84 / 28.72 | 4.6% |
| 32768 | 40540 / 3675 | 35514 / 8701 | 527.05 / 24.35 | 523.34 / 21.28 | 12.6% |
| 112000，两位置范围 | 40560–40561 / 3654–3655 | 35514 / 8701 | 395.76–397.69 / 13.13–13.82 | 392.62–394.23 / 10.63–10.78 | 17.8%–23.1% |

MB沿用npu-smi原始单位，总量44215MB。上表是阶段结束快照，不能叫逐请求全程峰值。8K/32K预热后三轮中位，112K每位置一次。相对各自8K，32K Decode下降C16约19.1%、C8约25.9%；112K下降C16约54.1%–56.4%、C8约62.5%–63.0%。

已有10秒间隔采样观测到C16最高40561MB、C8最高35518MB；C16采样覆盖启动及测试，C8长测采样未覆盖首次启动。因此它们是已观测最高值，仍可能漏掉瞬态峰值。按当前固定112K预留档，保守沿用该观测上界，各种输入长度的余量均约C16 3654MB、C8 8697MB，不存在明显随当前输入线性减少的可分配内存。

若在观测最高占用之外再预留约2GiB工程缓冲（本表按2048MB计），C16剩余约1606MB，C8剩余约6649MB。2GiB是本轮规划建议值，不是经过业务并发压力测试的保障值。不能通过单纯调低gpu_memory_utilization保证相同上下文与最小峰值；需要控制实际分配页数并验收。

预算计算：将npu-smi的MB数值按÷1024换算为GiB，总量约43.18GiB；这不是把标称48GB直接视作48GiB可用。基线保守取两档已观测峰值扣实际缓存池和C8工作区后的较大值，约29.32GiB；包括模型、非KV、运行时和设备其他占用，假设不随档位变化。固定已审计页布局1152token，最低页数为ceil(total_context/1152)+7（3个GDN组各2页+null页）；C16实际每页49545216字节，C8每页37380096字节；C8共享工作区为ceil(total_context/64)×64×2048字节。较小档位真实重启时页布局、Graph或工作区可能变化，须重新审计。

generate.py从原始内存审计生成capacity-estimates.json及capacity-table.md。原始依据见[配对实验](../clt-kv-comparison-20261015/README.md)。未计入额外并发、Prefix常驻多请求、视觉、其他NPU服务；不对32G或更大极限上下文做可用声明。

## 部署决策

48G/112K单流默认选C16，保留现有MTP1和Decode Graph。当前阶段仍使用原来223页的C16自动配置，避免把“核算可省”直接当成“服务已优化”。下轮若要降低实际预留，先以112K最小页数附近留余量的独立配置验证启动、长Prefill/Decode峰值与正确性，再逐步收紧；不要直接把最低107页当作生产保障。

C8适用于C16不能满足目标容量的档位，或后续获得更快INT8 KV Attention时重新评估。Prefix命中能减少重复Prefill，但本身不改变启动时预分配缓存预算。

# TP1/48G 实验 Profile

本文固定当前 Qwen3.6-35B-A3B 单卡 310P、W4A8、C16/C8、Decode Graph 的启动入口。唯一默认业务档为 `long-prefill`；`compat` 和 `decode` 保留为内部诊断及回归对照，避免 MindIEQ 修复后无法识别 Decode、MTP 或 Graph 的回归。profile 固定调度和已测后端组合，不改变权重或算子制品。参数解析集中在 `configs/tp1-profile.sh`，`--check` 和真正启动共用。

| profile | MTP | speculative tokens | Graph capture | batched tokens 默认值 | 适用场景 |
| --- | ---: | ---: | --- | ---: | --- |
| `compat` | 1 | 1 | `1,2` | 1024 | 兼容性基线、问题定位、MTP1 对照 |
| `decode` | 2 | 2 | `1,2,3` | 4096 | 当前单流 Decode 候选 |
| `long-prefill` | 2 | 2 | `1,2,3` | 2048 | 对外长上下文档；必须启用 MindIEQ，短输入按阈值回退 |

`mtp1` 和 `mtp2` 仍作为旧命令的兼容别名，分别映射到 `compat` 和 `decode`。当前候选入口默认选用 `long-prefill`，自动启用 E5 的自定义 A8、Gate/Up 共享和阈值128短请求回退。这是长上下文实验候选的默认选择，完整业务质量、并发和尾延迟门禁仍待完成。旧 C8/GDN wrapper 保留显式基线参数用于诊断，不作为业务推荐入口。

## 启动与校验

先准备 `MODEL_DIR`、`OPP_DIR`、`EXTENSION`、`C8_LIBRARY`、`GDN_OPP_DIR`、`GDN_LIBRARY`、`GDN_SOURCE` 和 `MINDIEQ_LIBRARY`，再执行：

```bash
scripts/run-candidate.sh --check  # a2默认MTP2，唯一业务档long-prefill
NUM_SPECULATIVE_TOKENS=1 scripts/run-candidate.sh --check  # clt当前MTP1，仍启用MindIEQ
scripts/run-candidate.sh --check --profile compat  # 内部MTP1对照
scripts/run-candidate.sh --check --profile decode  # 内部原W4对照
```

校验输出包含规范化 profile 名称、解析后的 `effective_config`、权重索引和所有动态库的 SHA256。真正启动时去掉 `--check`。`long-prefill` 默认开启 MindIEQ，显式关闭会被拒绝；自动选择已测 E5 的自定义 A8、Gate/Up 共享量化和默认阈值128，不允许关闭这两个 E5 特性，且阈值不能低于128；不启用 MindIEQ 的同参数服务统一使用 `decode` 档作为内部对照。

## 选择原则

`compat` 用于回归和故障隔离，避免把 MTP2 的接受率或 Graph capture 问题混入算子判断。`decode` 是原始 W4 的内部运行基线，优先观察单流 TPOT、MTP 接受长度和稳定性。`long-prefill` 是业务候选，必须启用 MindIEQ，并同时通过长输入 P50/P95、TTFT/TPOT、完整质量集、needle 正确性和服务生命周期门禁，不能仅凭短请求收益替代端到端验收。对外只推荐 `long-prefill` 启动档，保留两个诊断档的代码路径。必需设置 `MINDIEQ_LIBRARY`，校验器会记录其SHA256；缺失时拒绝启动，不静默回退到另一档。

每个 profile 都保持 `MAX_MODEL_LEN=114688`、`MEMORY_UTILIZATION=0.95`和 Decode Graph；公开48G/112K入口默认C16，`QWEN36_C8_ENABLED=1`可覆盖；长上下文容量需要结合实际 KV 分配、请求生命周期和 P95 结果单独记录。

## 不初始化 NPU 的回归校验

```bash
python3 tools/check_profile_launch.py
```

该工具使用临时占位制品和捕获参数的 Podman 替身，验证 `effective_config` 与真正启动入口构造的容器参数一致，并拒绝不满足 E5 约束的 `long-prefill` 配置。它只验证参数传递，不证明占位制品可加载，也不替代真实设备启动。

## 2026-10-15 KV默认值更新

a2/EP310P3的MTP2配对与clt/EP310P1的MTP1独立测试均显示，112K下C8的Decode代价明显，而按相同调度容量核算净省约1GiB。48G/112K公开入口因此优先C16，保留C8实验后端。详细样本、接受率、实际预留池与估算边界见[a2记录](../results/a2-kv-comparison-20261015/README.md)。旧实验wrapper保持原默认用于历史复现，必须从`run-candidate.sh --check`确认有效参数，不能靠服务名判断KV格式。RC另行验证，不自动继承EP的KV和MTP默认值。

## 主机之间的参数差异与收束门禁

三台机器均已实际尝试C16/MTP2/2048，不能再把主机差异仅归为实验不足。当前配置如下：

| 已验收环境（含当前追溯别名） | 硬件范围 | KV | MTP草稿数 | batch/chunk | 调度/prefix |
| --- | --- | --- | ---: | --- | --- |
| x86_64 / EP / driver26.1.1（a2） | 310P3，48G档 | C16 | 2 | 2048/512 | async / off |
| x86_64 / EP / driver26.0.t1（clt） | 310P1，可见44215MB | C16 | 1 | 2048/512 | sync / off |
| ARM64 / RC / driver7.6.T7.0.B053（orangepi） | 310P1，共享内存，非物理48G验证 | C16 | 1 | 4096/512 | sync / on |

共同启用TP1/W4A8/Decode Graph/GDN/MindIEQ，max_model_len114688。clt利用率.90，a2为.95；RC保留标称3GiB KV预算、.45利用率和multimodal blocking H2D适配，不能照搬EP的内存参数。a2本轮32K、112000+128、112K会议更新及长后短题均通过；clt恢复原已通过112K的MTP1容器后，短题8/8及A/B/A通过。RC的2048完整长验收通过，但Prefill回退，恢复原已验证4096；恢复短检查及原始数据以[统一部署记录](../results/unified-2048-20261015/README.md)为准。

[a2同协议MTP1/2 × batch2048/4096对照](../results/a2-profile-matrix-20261015/README.md)已完成：32K相同输入、相同输出、接受率100%时，MTP2在两种batch下均比MTP1提高Decode约23%，Prefill损失不足1%；固定MTP后2048/4096的32K速度差在0.3%以内。两个正式样本仅作筛选，不是P95或会议业务质量证明。2048用于减少部署分歧，未证明更快或峰值内存更低。上述batch结论仅属于a2：RC历史C8配对4096 Prefill约+11%，本轮C16/2048的32K约515.50，相对历史C16/4096的568.13低约9.3%，112K为389.57对420.53，低约7.4%，Decode基本持平。C16比较跨服务窗口，不视为严格交替A/B；结合历史RC C8配对结果，本轮恢复RC4096例外。

MTP2例外有实机证据：clt同步/异步均在rejection sampler异常申请数十万GiB；阻塞上传计数的局部修复虽消除该异常，正确性只有5/8，不接入默认代码。RC同步路径卡在draft event等待，异步路径出现507018/aicpu exception；独立六项D2H复制事件探针却全部通过，仍需定位完整模型的协议。具体日志、局部修复边界与回滚入口见[本轮报告](../results/unified-2048-20261015/README.md)。这些结果不证明310P1永久不支持MTP2。

公开入口保持一个long-prefill，默认MTP2；当前clt使用NUM_SPECULATIVE_TOKENS=1，自动配套capture1,2，MindIEQ和2048/512保持启用。RC使用其Docker兼容入口的MTP=1及MAX_BATCHED_TOKENS=4096。a2使用capture1,2,3。不要用compat档代替此覆盖，否则会改变MindIEQ和batch等其他变量。

## 推荐参数不绑定SSH名称

上表按已验收环境描述，括号内主机别名仅用于寻找原始记录、地址和运维入口。服务器改名不改变推荐参数；同型号新设备也不能仅凭310P1/310P3或RC/EP自动继承全部参数。当前入口没有按hostname自动选参数。

每次部署保留SoC/RC-EP、主机架构、可见内存、driver/firmware、CANN、镜像digest、源码和OPP/扩展SHA、调度方式及有效参数，验收通过后才将该组合标为适用。机器地址和容器路径放部署记录，算法选择依据留在本文及results。MTP1是当前两个环境的兼容性基线，不是310P1硬件规格。

### 本轮只读版本及源码核对

三环境CANN均为9.1.0、内部构建V100R001C11SPC001B243，torch2.10.0+cpu、torch-npu2.10.0.post4、vLLM0.23.0+empty、transformers5.5.4。EP的vLLM-Ascend包标记0.23.0.post1，RC为0.23.0。驱动与主机架构见上表，不能把这三台直接视为只改变SoC或RC/EP的受控实验。

实际文件核对进一步缩小了范围：三环境通用rejection_sampler.py及310P专用sampler的SHA256相同；两个EP的model_runner_v1.py也相同。RC runner相对EP的差异是dummy执行时将slot_mapping填-1移到attention metadata构造之后。该差异涉及状态准备顺序，值得隔离测试，但没有证明是MTP2失败根因。运行时bootstrap、Graph/GDN制品及驱动仍需一起比较；不能从源码文件相同推导执行语义一定相同。

证据在[本轮结果目录](../results/unified-2048-20261015/README.md)每个环境的runtime-versions.json、source-versions.json，以及runner-diff.txt。版本采样只读，不升级驱动或修改已恢复服务。

### 为什么采用这些参数

| 参数 | 当前选择 | 实验依据与适用边界 |
| --- | --- | --- |
| KV格式 | 48G/112K优先C16 | EP配对中C8约净省1GiB（同容量核算）但112K Decode低约18%～23%；RC方向性结果同样下降约21%，跨重启/预算变化，尚非严格交替A/B。不是所有内存档都禁用C8。 |
| MTP草稿数 | 通过门禁的环境用2，其余当前用1 | EP310P3同协议32K Decode约+23%，Prefill损失<1%；另外两个环境MTP2实测运行或正确性失败。先修复再复验，不将故障归为硬件上限。 |
| Decode Graph | 开启，capture随MTP1/2选1,2或1,2,3 | 已有启动、生成及长后请求状态门禁；当前仍依赖实验兼容层，不能认为所有新版Graph都可直接替换。 |
| MindIEQ | E5分流，min_tokens128 | 同输入重复对照有Prefill收益；小输入走原W4，Decode仍保留原路径。 |
| Prefill batch | EP参考2048；当前RC4096 | EP310P3固定MTP后2048/4096差异<0.3%；RC C8控制变量测试4096约+11%，本轮C16/2048的32K/112K也较历史4096低9.3%/7.4%。不是RC模式理论上必须4096。 |
| Expert chunk | 512 | 当前已验证实现的处理块，含义不同于scheduler的batched tokens；本轮未做跨硬件chunk最优性证明。 |
| 上下文 | max_model_len114688，实际验收112000+128 | 是已测单流规格，不是KV日志容量或绝对最大输入；完整业务质量及P95另验收。 |

### 后续归因顺序

1. 固定权重、量化元数据、GDN/算子制品来源和采样协议，补齐运行时patch及firmware指纹；保持可回滚基线。
2. 优先隔离MTP2的草稿计数上传、事件同步与Graph状态准备。局部修复必须同时通过采样器数值、短题、A/B/A、长后请求，再测收益；clt的blocking-count补丁已因5/8被拒绝，不能作为通用修复。
3. 在隔离容器或worktree中统一相关软件路径，逐项比较sync/async、Graph开关和上述slot_mapping顺序；不同时升级驱动、改调度、换算子后再声称归因。
4. 软件与任务形状对齐后若差异仍稳定存在，再比较EP/RC传输/同步、CPU调度及设备kernel计时；需要同SoC跨RC/EP或相同模式跨P1/P3的受控硬件条件，才能提出硬件因果结论。
5. Prefill优化按真实专家token分布/形状与batch交互分析Cube/向量、路由分桶及launch时间。候选解释是增大scheduler batch会减少Prefill分块迭代及其路由/launch开销，同时改变每个专家GEMM形状；ARM主机开销可能放大此收益，但这仍是待profile证明的假设，不是RC4096收益的已确定根因。本轮RC4096收益已可用，详细kernel归因尚未完成，不继续把已验证参数扫表当作硬件解释。

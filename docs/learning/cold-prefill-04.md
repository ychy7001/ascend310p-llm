# Prefix cache 固定到达回放与 32K Prefill 时间线

2026-11-14，在 `ychy-a2` 的 Atlas 300I DUO 上使用固定验收镜像 `bb0fa66f…` 和只读 W8A8 权重，使用镜像入口副本，仅多传 profiler 参数。保持 TP2、262144 上下文、seq4、主 Graph `[3,6,12]`、MTP2/draft eager、async 和 prefix cache on，只改每轮 token 预算 2048/4096。每档各一次独立冷启动，在 `/tmp/a310-npu.lock` 内完成。按[前一轮](cold-prefill-03.md)分开看聚合吞吐与流式体验。

每轮先在独立 salt 下发送 16384-token 冷预填请求，随后在 0、0.35、0.90、1.60 秒投递 14336/192 暖跟进、32768/256 冷长请求、1024/128 冷短请求、15360/192 暖抽取（输入/输出 token）。暖两路共享前 12288 token 和 salt，其余请求使用不同 salt。每档五轮，预填耗时不计入回放墙钟；普通回放身份可由 plan 和 token ID 哈希核对。合成文本模拟会议问答/抽取的形状，不代表真实业务语义或线上分位数。

普通计时结束后，每档独立采一条冷 `32768+1`（唯一 salt，zero hit），同镜像离线导出两 rank。采样耗时不参与回放。按每 30 次原生 `ComputeWy` 划出近似 forward 段；段首在首个 WY 处，边界前的投影/搬运会被分到前一段。按 kernel 名累计，不跨 rank 相加，也不当作墙钟归因。

| 五轮中位数 | 2048 | 4096 |
|---|---:|---:|
| 回放墙钟 | 43.315 s | 42.897 s |
| 聚合输出吞吐 | 17.731 tok/s | 17.903 tok/s |
| 暖跟进 TTFT / 最长文本间隔 | 1.940 / 1.864 s | 1.955 / 3.656 s |
| 1K 冷短请求 TTFT / 最长文本间隔 | 13.800 / 1.864 s | 14.483 / 3.656 s |
| 暖抽取 TTFT / 最长文本间隔 | 30.283 / 0.259 s | 29.669 / 0.261 s |
| 32K 冷长请求 TTFT / 最长文本间隔 | 29.291 / 1.516 s | 30.198 / 0.717 s |

40/40 条普通计时请求通过，输入哈希和实际 CLI（屏蔽预算值）一致。每档每轮暖两路各从响应 `usage` 确认命中 11,520 token，冷两路和预填为零。服务端指标每轮增量为 115,200 / 69,120（2048 / 4096）；这与逐请求 usage 口径不同，不作为唯一命中量。客户端最大发起偏差 <1 ms。4096 聚合中位仅高 0.97%，暖跟进和短冷流的停顿在五轮都接近翻倍；保留交互默认 2048。只有一次 A/B 启动对照，没有业务语义验收或生产分位数。两档报告 KV 池均 632,375 token，采样后短 JSON 通过；两个容器退出码均 0，独立检查确认 a2 设备、端口和锁清场。未操作 a1、未改部署。

32K 冷采样两档均零命中，四份 rank CSV 完整。2048 每 rank 540 次 WY，按 shape 分为 `16×1920 + 1280 + 768`；4096 每 rank 300 次，分为 `8×3840 + 1280 + 768`。两档的实际形状合计均为 32768；prefix on 日志显示 hybrid Mamba cache 为 `align`。不能把调度预算直接当成每段长度。

| 32K 采样项 | 2048，双 rank 各自范围 | 4096，双 rank 各自范围 |
|---|---:|---:|
| 设备 timeline 跨度 | 22.508–22.516 s | 21.567–21.576 s |
| 命名 kernel 区间覆盖 | 97.56–97.61% | 98.24–98.56% |
| 分页 Attention 累计 | 5.80–5.81 s | 5.99–6.00 s |
| W8A8 MoE grouped matmul 累计 | 4.70–4.73 s | 3.63–3.66 s |
| TransData 累计 | 0.83 s | 0.96–0.97 s |

在 2048 的等长 1920-token 段中，rank0 分页 Attention 从第 2 段约 76 ms 增至第 16 段约 606 ms，MoE 同期约 274→259 ms；rank1 同向。4096 减少了 MoE 调用次数（1440→800/rank）与累积耗时，但分页 Attention 累计不降。这个结果把**历史长度越长时的优先优化点**定位到了分页 Attention，并没有证明瓶颈具体是 KV 带宽、mask 生成还是 kernel 内部实现。建议下一步固定 2048，以同 query 长度分离不同历史长度，拆测分页 Attention、mask/搬运，用数值门禁保护 GDN 和 KV 语义；不要为了省 MoE 调用直接把交互默认预算抬高。

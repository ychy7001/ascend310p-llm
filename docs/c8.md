# C8 独立实验复现

C8同时提供独立算子与受限的完整模型实验后端，不需要新的模型权重；动态per-token/head scale在cache写入时生成，K/V为INT8，scale为FP16 padded `[slots,16]`。GQA为16Q/2KV、dim256，测试block64，另验证block128/dim128。invalid页zero-fill只用于内存保护，不代表有效历史。

在310P镜像内，挂载仓库为`/project`，安装相匹配driver并只暴露目标NPU，禁用不兼容Triton后：

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
cmake -S /project/experimental/ascend_c8_kernel -B /work/c8-build \
  -DSOC_VERSION=Ascend310P3 -DCMAKE_BUILD_TYPE=Release \
  -DC8_NZ_TRANSDATA=ON -DC8_NZ_MAX_TILE=64 -DC8_NZ_COMPACT_SCALE=ON
cmake --build /work/c8-build -j4
python3 /project/experimental/check_c8_selected_nz_310.py --library /work/c8-build/output/libqwen36_c8.so
python3 /project/experimental/check_c8_selected_nz_310.py --library /work/c8-build/output/libqwen36_c8.so --block 128 --dim 128
python3 /project/experimental/bench_c8_vs_fp16_paged_310.py --library /work/c8-build/output/libqwen36_c8.so --cube --splits 4 --staged --lengths 4096 32768 --profile-dir /work/c8-profile
```

matched tile32的DMA双缓冲对照：设置`C8_NZ_MAX_TILE=32`，分别`C8_NZ_PIPELINE=OFF/ON`，使用全新build目录，交替运行上述benchmark。默认所有NZ优化选项OFF；高宽度UB预算未穷尽验证，不能将已测width256/512推广到全部输入。

`--cube`是融合Cube候选，已通过数值与Graph，但32K仍约8ms；`--staged`是独立C8→临时NZ→原生PA对照。5warmup/20repeats，host与device profile分开看。库内部cast采用CAST_NONE，避免已在310P暴露的float→half CAST_RINT问题。

混合Mmad的编译探针在`experimental/c8_mixed_mmad_probe`：混合版本预计失败，`-DPROBE_FP16_CONTROL=ON`控制组可编译。它没有可执行的初始化输入，**不要运行探针kernel**。这只验证当前基础API类型能力，不断言硬件所有能力，也不否定mad_s4的INT4路径。

## 完整模型接入候选（初版短生成已通过）

`experimental/c8_vllm_adapter.py`与`run-c8-service.sh`为TP1/eager/MTP=0/单请求候选，暂不属于生产支持配置。保持linear state浮点，full attention使用独立INT8 K/V与FP16 padded scale；历史读取选页转换到跨层共用的FP16 NZ，然后调用原生PA/splitfuse。初次无历史prefill消费当前浮点K/V。

明确限制：当前保留hybrid page padding，把原共享池改为独立层缓冲区，并根据原预算减少scheduler blocks、预留一份max-context NZ；它旨在先验证真实C8生成，**不声称模型级容量改善**。真正容量后端还需降低padding与改善共享布局。adapter显式接入`NPUModelRunner310._allocate_kv_cache_tensors`；310P覆写通用分配/reshape，不能只patch通用runner。另先初始化ops package避免DeviceOperator/fused_moe循环导入。

在a2同环境设置`MODEL_DIR`、`OPP_DIR`、`EXTENSION`和`C8_LIBRARY`为已验证制品的绝对路径，执行`bash experimental/run-c8-service.sh`。默认18016/4K/.90、max sequences=1、batched tokens=256，prefix cache关闭。检查日志的`C8_ALLOCATOR`、`C8_STORAGE`和真实请求`C8_FORWARD`，必须是四张量cache；health通过也不等于生成通过。完成门禁后追加结果；当前没有W4A8+MTP+C8联合验收。

experimentally verified（2026-10-12）：a2真实310P3，配合公开checkpoint与新编译W4算子，TP1/MTP=0/eager/4096/.90启动及五类生成sanity通过，completion tokens=64/64/35/64/64；内容可读，长解释截断，不证明准确率。十个full-attention层确认INT8 K/V与FP16 scale；独立40层总allocation=5,284,823,040 bytes、scheduler blocks=56，原预算=5,308,416,000；NZ共用8,388,608 bytes。每个full层64512slots、有效data/scale=70,189,056 bytes、实际allocation=132,120,576 bytes，padding=61,931,520 bytes。页对齐仍抵消压缩收益，不声称此轮模型内存净节省。

1warmup+3rounds：p512/o64为13.3899/13.1155/13.2868tok/s，TTFT=1.6407/1.7487/1.6781s、请求平均TPOT≈49.7–49.8ms；p3072/o32为2.8152/2.8169/2.8050tok/s，TTFT≈9.78–9.83s、TPOT≈50.83–51.05ms。max batched tokens=256，因此两组均覆盖chunked prefill，连续请求也覆盖页释放再分配；尚未做严格质量差分或请求隔离专项检查。吞吐包含prefill/HTTP；重复token工作负载不是质量样本。同配置FP16 KV对照已完成，见下表；不与先前MTP开启结果直接比较。

`QWEN36_C8_ENABLED=0`可在同一实验启动器关闭C8 adapter，运行普通FP16 KV对照；其服务名沿用实验名，仅为保持HTTP benchmark参数一致，不代表启用了C8。默认值1才加载adapter，关闭时日志应不存在`C8_STORAGE`。原始结果保留a2 release目录`c8-bringup-310allocator.log`、`c8-generation-sanity.json`、`c8-p512-o64.jsonl`和`c8-p3072-o32.jsonl`。

## 匹配FP16 KV对照（2026-10-12）

experimentally verified：同一W4 checkpoint、OPP/extension、TP1/eager/MTP=0、4K/.90、max-seqs1/max-batch256，关闭prefix caching。每组1warmup/3rounds，prompt IDs逐项相同。以下为中位数，tok/s含prefill/HTTP；TPOT为每请求平均值的中位数。

| 输入/输出 | FP16 KV tok/s / C8 tok/s | FP16 / C8 TTFT s | FP16 / C8 TPOT ms |
| --- | --- | --- | --- |
| p512/o64 | 14.2881 / 13.2868 | 1.6193 / 1.6781 | 45.40 / 49.80 |
| p3072/o32 | 2.9583 / 2.8152 | 9.3947 / 9.7878 | 45.90 / 50.91 |

当前C8吞吐分别下降7.01%/4.84%，请求平均TPOT增加9.69%/10.91%。五类sanity的FP16/C8结果均PASS；code/math/repeat文本相同，英文/中文不同。只证明有限样本可生成，不是量化质量等价证明。原始对照日志`fp16kv-control.log`、`fp16kv-generation-sanity.json`、`fp16kv-p512-o64.jsonl`、`fp16kv-p3072-o32.jsonl`留在a2 release目录。

物理紧凑分配候选：从逻辑charged page数量计算slots，仅分配实际K/V与scale连续payload，省去不被view访问的尾部padding；scheduler的原page预算和block数保持保守，不把省下的物理空间直接宣传为新增上下文容量。experimentally verified：该候选真实310P重新启动、五类生成与两组1warmup/3rounds benchmark通过。十层总物理payload减少619,315,200bytes（590.625MiB），每层实际70,189,056bytes，charged仍132,120,576bytes，scheduler仍56blocks。p512/o64中位吞吐13.4352tok/s、TTFT1.6524s、TPOT49.319ms；p3072/o32为2.8361tok/s、9.7148s、50.759ms。仍慢于匹配FP16 KV。npu-smi观测设备内存约31098MB、进程29434MB，是运行中快照而非峰值或严格分配归因；整模型峰值/容量门禁仍待完成。日志c8-compact.log及c8-compact-*.json/jsonl留在a2 release目录。

## W4A8 + MTP + C8有限联合实验（2026-10-12）

experimentally verified：统一目标与drafter的full-attention C8 spec后，TP1/eager/4K/.90/MTP=1、max-seqs1/max-batch256通过启动。日志C8_BUDGET：4groups、41layers、原132blocks、独立35blocks、最低8blocks，charged bytes/block=96,731,136，原预算3,425,697,792bytes，独立charged=3,385,589,760，NZ scratch=8,388,608。MTP层确认INT8 K/V+FP16 scale；权重仍为原BF16 MTP。初版float drafter KV候选在budget门禁失败；分组源码以最小同类层数分组，dtype/spec分裂导致碎片化是原因推断，不伪造首轮未记录的group计数。

8小题严格答案8/8、3K干扰A/B/A通过；该批53draft全部接受，不能证明实际拒绝覆盖。随后固定GSM8K32题（协议见quality.md）32/32、0解析缺失、0截断，6875输出tokens，总请求计时288.25s（不是性能基准）。GSM计数器增量3496draft/3365accepted，131reject，接受率约96.25%；之后再次8/8与A/B/A通过。它覆盖有限实际拒绝与跨请求复用，不证明全部linear state回退或完整精度。FP16 KV+MTP匹配质量对照已启动，结果待补。

独立拒绝槽原生PA探针prefix63/64/127全部PASS：未来draft在有效长度外不可见；覆盖被拒绝位置后与干净C8输出max_abs=0。它只检验C8存储和PA语义。

非融合写入的MTP=1首轮HTTP基准（1warmup/3rounds，含prefill/HTTP）：p512/o64三轮14.7750/15.0468/14.8084tok/s；p3072/o32为2.9227/2.9200/2.9276。尚无相同FP16 KV+MTP对照，不据此宣称最终加速。raw日志c8-mtp-uniform.log、c8-mtp-reuse-quality.json、c8-mtp1-gsm32.jsonl、c8-mtp1-post-gsm-metrics.txt、c8-mtp-post-gsm-reuse.json、c8-mtp-p*.jsonl。

## 融合动态量化写入候选

先测未融合write：单token约300us，原生FP16 reshape/cache约43us；5次profile中C8约32kernel/次，FP16为1kernel。NPU纯kernel累计远低于host launch+synchronize，主机调度/小kernel链是可观察的成本，不能将host时间全归为硬件计算。

新增c8_quant_scatter：FP16 K/V→per-token/head amax→存储的FP16 scale（tiny clamp）→round/clamp INT8→slot scatter，一次launch写K/V及两份scale；仅支持dim128/256、heads1..16，真实门禁测heads2。复用已验证310P activation-pack的reduce/cast顺序；默认`QWEN36_C8_FUSED_WRITE=0`，显式1才使用新库中的operator，旧库不支持该flag。

真实310P3编译与数值通过：原cache测试（近零、padding、页、decode、multiquery因果）、拒绝槽探针；原生PA覆盖对照max_abs=0。profile确认融合write仅1个kernel。独立库SHA256 `ee91aac12582a05f1581580d2e1499a2446bf698d202a62c24641c6edb084755`。首轮host注册代码const指针列表编译失败已修正；SDK增量预处理重链旧.o失败，改全新v2 build通过。

| tokens | 未融合C8 us | 融合C8 us | FP16 write us |

| 1 | 533.30 | 49.92 | 50.49 |

## 按存储类型拆分共享池候选

source-code verified：当前镜像get_kv_cache_config_from_groups将同一位置各group的层列入shared_by；不同group采用不同block table，从全局block pool领取不同block IDs。原生310P linear allocator也在同pool内复用state tensors。独立41层方式按所有层计费，降低了scheduler blocks。

新增显式`QWEN36_C8_POOL_MODE=split_by_type`候选：保留上游shared_by映射和group/block IDs，仅将每个pool拆成C8与linear两种物理池；C8按INT8 K/V+FP16 padded scale实际payload计费，linear保留原padded page，不让两种布局互相alias。重算每scheduler block实际总字节、预留NZ scratch、blocks仍不超过上游原num_blocks；同类共享层必须spec完全一致。默认independent，候选设备验收待完成，不声称已支持长上下文或新增容量。

融合write已另通过heads1/2/16、dim128/256、tokens1/2/65/4096的随机数/近零/乱序padding slot与unfused对照（允许1INT8 bin），以及动态query输入、scale、slot的NPUGraph回放。该Graph只覆盖独立write，不是完整vLLM模型Graph。raw c8-fused-write-parity-graph.log留a2；数值测试与FP16质量HTTP同时运行，因此该时段质量响应elapsed不能用于性能归因，之后的HTTP性能基准顺序单独运行。

# C8 / INT8 KV：能力、实测结果与复现

## 1. 这部分解决什么问题？

C8 用分页 INT8 K/V 保存 full-attention 历史缓存，目标是探索 KV 存储的容量与性能权衡。它提供独立算子和受限的完整模型实验后端，无需新的模型权重：cache 写入时动态生成 per-token/head scale，K/V 为 INT8，scale 为 FP16 padded `[slots,16]`。linear state 保持浮点；读取历史时，将选中页转换到 FP16 NZ，再调用原生 PA / SplitFuse。初次无历史 prefill 直接消费当前浮点 K/V。

独立算子的主要测试形状为 GQA 16Q/2KV、dim256、block64，另验证 block128/dim128。完整模型 adapter 接入 `NPUModelRunner310._allocate_kv_cache_tensors`，适配 310P 自己的分配和 reshape 路径；初始化时先加载 ops package，避免 DeviceOperator/fused_moe 循环导入。

模型接入包含几种实验方案：

| 方案 | 做法与目的 |
| --- | --- |
| 独立层分配（默认 `independent`） | 保留 hybrid page padding，将原共享池改为独立层缓冲区；按原预算减少 scheduler blocks，预留一份 max-context NZ，先验证真实 C8 生成。 |
| 物理紧凑分配 | 从逻辑 charged page 数计算 slots，只分配连续 K/V 与 scale payload，去掉 view 不访问的尾部 padding；保留原 scheduler page 预算和 block 数。 |
| `split_by_type` | 保留上游 shared_by 映射及 group/block IDs，将每个 pool 拆为 C8 与 linear 两种物理池。C8 按 INT8 K/V + FP16 padded scale payload 计费，linear 保留 padded page；同类共享层要求 spec 完全一致。重算每 scheduler block 字节并预留 NZ scratch，blocks 上限仍为上游原 num_blocks。 |
| 融合写入 | `c8_quant_scatter` 一次 launch 完成 FP16 K/V → per-token/head amax → FP16 scale（tiny clamp）→ round/clamp INT8 → slot scatter，写入 K/V 和两份 scale。复用已验证的 310P activation-pack reduce/cast 顺序。 |
| Graph 设备有效长度转换 | 单元素 NPU INT32 `context_length` 指定当前长度，只转换向上取整的完整有效页；host 不读长度、输出 shape 固定，PA 使用同一实际 context_lens 遮罩。 |
| 持久化 NZ 单页直写 | `c8_cache_to_nz_range` 接收完整 C8 cache、单元素物理页表、完整预分配 NZ workspace 和目标 block，直接写一个 64-token kernel page；保留现有 `c8_cache_to_nz` ABI。 |

源码复核确认，镜像的 `get_kv_cache_config_from_groups` 把同一位置各 group 的层列入 shared_by；各 group 使用各自 block table，从全局 block pool 领取不同 block IDs。原生 310P linear allocator 也在同 pool 复用 state tensors。独立 41 层按全部层计费会降低 scheduler blocks；按类型拆池用于减少这部分分组浪费。

## 2. 已验证哪些能力，数据是什么？

### 2.1 如何阅读测量结果？

以下按场景组织，日期和版本用于区分实验。HTTP 吞吐包含 prefill/HTTP；HTTP 表中的 TPOT 是每请求平均值的中位数。阶段计时则使用独占端点前后的 Prometheus sum/count 差分，检查请求 count 增量为 1；Decode 公式为 `(output_tokens-1)/request_decode_time`，prefill_time 包含阶段调度与首 token 处理。各表保留原记录的数值精度，部分对照同时保留原文的精确值与摘要舍入值。

## 3. 怎么使用、怎么复现？

### 3.1 编译独立算子与运行基准

在310P镜像内将仓库挂载为`/project`，安装匹配driver、只暴露目标NPU、禁用不兼容Triton，然后执行原命令：

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
cmake -S /project/experimental/ascend_c8_kernel -B /work/c8-build \
  -DSOC_VERSION=Ascend310P3 -DCMAKE_BUILD_TYPE=Release \
  -DC8_NZ_TRANSDATA=ON -DC8_NZ_MAX_TILE=64 -DC8_NZ_COMPACT_SCALE=ON
cmake --build /work/c8-build -j4
python3 /project/experimental/check_c8_selected_nz_310.py --library /work/c8-build/output/libqwen36_c8.so
python3 /project/experimental/check_c8_selected_nz_310.py --library /work/c8-build/output/libqwen36_c8.so --block 128 --dim 128
python3 /project/experimental/bench_c8_vs_fp16_paged_310.py --library /work/c8-build/output/libqwen36_c8.so --cube --splits 4 --staged --lengths 4096 32768 --profile-dir /work/c8-profile
```

matched tile32 DMA双缓冲对照：设置`C8_NZ_MAX_TILE=32`，分别使用`C8_NZ_PIPELINE=OFF/ON`，全新build目录编译，交替运行上述benchmark。所有NZ优化选项默认OFF。`--cube`为融合Cube候选，数值与Graph通过，32K仍约8ms；`--staged`为独立C8→临时NZ→原生PA对照。该benchmark为5warmup/20repeats，host与device profile分别查看。库内部采用`CAST_NONE`，避开310P已暴露的float→half `CAST_RINT`问题。

混合Mmad编译探针位于`experimental/c8_mixed_mmad_probe`：混合版本预计编译失败，`-DPROBE_FP16_CONTROL=ON`控制组可编译。探针没有可执行的初始化输入，**不要运行探针kernel**。

融合write应在新目录编译新库，保留已测NZ transdata/compact-scale/tile64选项。首轮host注册const指针列表编译错误已修正；SDK增量预处理重链旧.o失败后，用全新v2 build通过。原有复现命令为：

```bash
QWEN36_C8_FUSED_WRITE=1 python3 experimental/check_c8_cache_310.py --library <new.so>
```

另执行拒绝槽探针，以及`bench_c8_cache_write_310.py --library <new.so> --compare-fused --profile-dir <new-dir>`同进程比较write路径。记录日志和profile目录，不进Git。设备有效长度独立测试代码为`bench_c8_device_length_310.py`，持久NZ独立probe为`experimental/bench_c8_range_kernel_310.py`。

## 4. 已知限制

- **结果适用范围与默认值。** 完整模型后端仍是受限实验候选，不属于生产支持配置；health通过不等于生成通过。已测结果支持48G上的性能/容量权衡候选；32G规格、最大上下文产品验收和无条件替换所有部署档位均未通过。C8仅量化Attention K/V，linear state、scale、FP16 NZ scratch仍占内存；相同utilization可能把省下的空间分给更多cache，需同时记录容量和实际请求长度，KV理论减半不代表整机内存减半。
- **数值、质量和请求隔离。** sanity可读、重复token性能负载、有限8题/A-B-A、GSM32和单needle各有覆盖边界，不构成正式准确率、量化质量等价、allocator隔离或全部linear state回退证明。独立拒绝槽探针只验证C8存储/PA；53 draft全接受一批没有实际拒绝覆盖，后续131 reject补充了有限覆盖。MTP linear state回退仍依赖官方hybrid/MTP机制，拒绝后的有效长度与overwrite需专项验证。初版chunked prefill/页复用不替代严格质量差分。原记录中的完整W4A8+MTP+C8联合验收仍未完成。
- **性能口径。** HTTP吞吐、请求平均TPOT、服务端阶段墙钟、host launch+synchronize、单kernel时间是不同测量。TPOT受MTP批量接受及HTTP分块影响；host调度时间不应全归为硬件计算。三轮/跨轮/序贯探索不保证小差值稳定，也没有可靠尾延迟或P50/P95结论；并发每档两轮同样只作探针。32K Graph Prefill含首token处理，其变化不能写成纯Prefill kernel改善9%。写入独立Graph和microbenchmark不代表完整模型Graph或端到端加速；融合write模型收益仍需更多重复。
- **比较条件。** A1 W8A8命令中的FULL_DECODE_ONLY与capture `[1]`仅是配置证据，具体请求用图需capture/replay日志或profile。A2早期eager与A1，以及4K初版Graph与A1 TP2 W8生产配置，不支持直接归因比较。早期4K p128/o256 Decode32.9694与128K p128/o64 Decode20.6136输出长度不同，非严格对照，4K速度不适用于128K宣传。第四轮质量失败的Graph吞吐仅作诊断；needle失败是否全部由CPU裁剪页数冻结导致仍缺同prompt eager/graph归因证据。首轮drafter FP16 KV的dtype/spec分裂及最小同类层分组导致碎片化属于原因推断，首轮未记录group数。
- **内存与容量。** 独立层初版没有模型内存净节省；紧凑分配的payload减少未增加scheduler预算，整模型峰值/容量门禁仍待补。block/page/slot增加、启动成功和单次检索各自不能替代长上下文质量、吞吐、峰值内存及并发验收，最初32K启动也不代表32K/128K/256K均验收。npu-smi快照与5秒设备总内存采样不是精确峰值或严格分配归因，组间差值不能直接代表Graph分配量；128K真实请求也不是交互式低延迟指标。C8/C16最终结论仍需64K/128K/接近上限同协议比较，综合启动上限、实际检索长度、长Prefill、固定输出Decode下降比例及KV/设备峰值。
- **Graph与长配置。** 第二/第三轮Graph失败没有可服务后端或收益数据；首轮FakeTensor失败发生在C8捕获前，不能推断C8或310P硬件不支持图。mode3在split-graph阶段仍有“节点有两个用户”的失败，mode0绕过该路径；updatable参数更新依赖实验monkeypatch/诊断开关，需要正式backend修复。64K普通Graph也曾因`graph_params=None`初始化失败。112K短/中输入尚无稳定Graph收益，需要与eager/A1 W8A8使用相同unique prompts交替复测。MTP2的后续同协议交替基线已有结果，仍需更大真实业务样本接受率、P95和正式backend验证后决定默认值。
- **算子输入与读写语义。** NZ高宽度UB预算未穷尽，width256/512结果不能推广全部输入。invalid页zero-fill仅为内存保护，不代表有效历史。混合Mmad探针只反映当前基础API类型能力，不代表全部硬件能力，也不否定mad_s4 INT4路径。设备有效长度当前仅TP1/单序列，未转换区域可保留旧值，必须依赖PA context_lens遮罩，不是通用完整缓存读取接口，不能推广多请求或128K配置收益。初次device-length测试出现过Triton import、设备映射和驱动初始化失败，失败日志已保留。写入数值测试曾与FP16质量HTTP同时执行，该时段响应elapsed不能作性能归因，后续性能基准已顺序独占运行；counter检查也不能代替端点独占。
- **持久NZ原型。** 单页kernel尚需动态block-table、Graph目标页更新、页回收/重排和多请求并发门禁；adapter接入尚无模型级正确性/性能验收或端到端Decode收益。每层独立workspace额外占显存，不能作为产品参数。默认路径恢复与4K实验的`mode=full`只能证明全量路径可启动，尚未证明调度进入range；下一步需记录每次forward的`attn_state`、`num_actual_tokens`及ready状态，再修正条件。
